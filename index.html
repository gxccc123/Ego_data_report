METHODS · EXPERIMENTS · DATA CONTRACT

第一视角视频的三维手部轨迹重建

从相机系手部估计到世界系轨迹：方法、误差分析与数据交付

技术整理：2026-09-19 · 实现基线：3c58fd2 · 历史实验与产物回查分开记录

新增：2026-09-21 跨数据集测评汇报，独立整理 MINT / ACE / HaWoR / OLA 实测、检测诊断、完整流程审计与采集建议。本页保留原管线技术说明与历史实验口径。

这条管线要解决的是：给定一段第一视角 RGB 视频，估计左右手逐帧的三维关节位置，并尽可能去除头戴相机运动带来的影响，生成能够与原视频、已有子任务标注对齐的手部几何资产。它不是重新人工标注动作文本，也不直接生成某种机器人的关节控制指令。

难点不只是“在画面中找到手”。单目手部模型需要估计不可直接观测的深度；相机轨迹需要恢复尺度；独立运行的短片段需要对齐；输出中还会保留漏检、遮挡、身份切换和跳变。本文先按实际调用链解释处理过程，再用已有定量记录与失败案例说明：当前产物能支持什么，哪些问题仍不能由一次成功运行来证明。

核心结论

  • 当前主线：RGB / 内参 → HaWoR 相机系手部 → 手部 mask + DROID-SLAM → Metric3D 尺度恢复 → 重叠片段拼接 → 世界坐标变换 → QC / 有限修复 → NPZ。
  • 能力边界：沿用 HaWoR 的估计核心，增加数据适配、调度、标准化与交付机制；推荐流程跳过 infiller，不执行 world-space smoothing。不能视为完整官方流程的原样运行。
  • 已有证据：历史单序列的关节误差中位数为 60.7 mm，最好右手样例为 9.1 mm，但最差可达 391.4 mm。有效帧覆盖和几何精度必须分开报告。
  • 交付目标：与视频可对齐的 hand_joints_3d.npz、质量报告、来源信息及 1–2 个可视化样例；通过现有 converter 再进入训练格式。两份回查的 CaptainCook4D 产物均仍为 warning / review。

阅读口径：方法依据当前仓库源码；评测数字来自提供的《3D 手部轨迹重建》报告；生产案例来自 2026-08-11 产物、于 2026-09-19 回查。本次整理没有新增模型推理，也不声称全量数据已经完成或质量已验收。

1. 任务定义：补的是几何，不是再做一遍语义标注

完整的人类操作训练样本通常需要三类信息：看到什么（视频观测）、在做什么（时间段及语言描述）、手如何移动（逐帧几何）。本项目承担第三项，并保留与前两项连接所需的时间轴和来源标识。

与 HaWoR、VITRA 的关系

HaWoR 本身面向第一视角视频的世界系手部运动重建，因此“手部 + 相机 + 世界坐标”并不是本工程新增的算法思想。我们复用其模型和相机估计部件，把它接入可恢复的数据生产流程。VITRA 的目标更广：把视频转成带原子任务片段、语言描述、手部和相机运动的 VLA 训练数据。这里的几何补标只是这类完整数据链路的一部分。

所以比较需要分层：工程可用性看多数据集适配、失败恢复和输出一致性；几何准确度看同样本、同帧掩码、同坐标协议的误差；训练价值看相同数据预算和训练设置下的下游收益。目前不能从工程步骤更多推出精度超过 HaWoR 或 VITRA，也不能用集合“真包含”准确描述几套系统的关系。

2.1 输入、时间轴与相机标定

import-ego-video 探测视频的帧率、分辨率和帧数，生成 episode.yaml 与切片范围。默认片长 20 s、重叠 1 s；按 FPS 换算并四舍五入到整数帧；末段长度不超过 10 s 时合并到前段。片段端点是包含式帧号，而下游切片 / 数组通常采用左闭右开区间，转换时不能省略这层约定。

L = round(20 · fps), O = round(1 · fps), stride = L − O30 fps 示例：clip 0 为源帧 0–599，clip 1 从 570 开始；共同帧为 570–599。末段合并会改变最后一个片长。

要同时保留 frame_indices、source_frame_indices 与 timestamps。前者是结果时间轴，第二个是回到原视频的索引，时间戳用于跨流和语义区间对齐。不能因为各文件都是 30 fps，就假定它们从同一帧开始或没有丢帧。

内参写作 K = [[fx, 0, cx], [0, fy, cy], [0, 0, 1]]。它必须对应实际输入图像的分辨率、裁剪和去畸变状态。例如先从原图裁去左上偏移 (x0, y0)，再按 (ax, ay) 缩放，则新主点为 ax(cx−x0)、ay(cy−y0)，焦距分别乘相应比例。这是应满足的几何关系，不意味着每份旧数据都已自动正确处理。

推荐 recipe 使用准备好的 dataset profile；它没有隐式启用所有数据集的去畸变，也没有自动回退到 DroidCalib。CaptainCook4D 旧分支存在 stride=2, num_images=80 的 DroidCalib 估计入口，但估计出的内参不等于原厂标定。内参 K 也不是外参：外参描述相机之间或相机到世界的变换，本单目流程是在后面估计时变相机位姿。

实现：clip_split.py · ego_video.py · dataset profile

2.2 HaWoR：从检测轨迹到 MANO 参数与三维关节

手部阶段先检测、跟踪手并构造裁剪序列，再运行 HaWoR。模型不是直接独立回归 21 个三维点：它由图像特征和时序模块回归 MANO 手部参数、形状及相机相关量，再经参数化手模型产生关节与网格。这样能够约束手型，但并不能排除错误深度、错误手别或时序失效。

仓库中的 HaWoR 实现包含两类可配置的时序处理：ST_MODULE 将图像特征与归一化 bbox 信息拼接后做时序 attention；MOTION_MODULE 对预测姿态及 bbox 信息再做时序处理。网络代码按 16 帧组织这些模块，内部姿态使用 6D rotation，随后转换为旋转矩阵。它们是否启用取决于实际模型配置，不应只凭类定义判断。管线的 hawor_motion_chunk_frames=64 是另一层推理分块参数，和外层 20 s clip、模型内部 16 帧都不是同一个概念。

MANO 生成的关节经映射与指尖补点整理为 OpenPose-21。此时结果处于 ego_camera_frame：即使手在桌面上完全不动，只要相机转头或平移，手的相机系坐标也会变化。要得到空间运动，需要独立估计相机并做后续变换。

一个重要的实际开关：主包装器显式附加 --skip_infiller。demo_moge.py 完成相机系手部结果后提前返回，独立的相机 step 随后执行。因此当前运行不包含官方 demo 后续的全部世界系 / infiller 处理，不能假设遮挡空洞已被学习式补全。build_hand_masks=false 则只是避免提前完整生成 mask；后续 SLAM 仍会按需渲染手部 mask。

2.3 相机轨迹：动态区域屏蔽与 Metric3D 尺度恢复

相机阶段首先将 HaWoR 网格投影成手部 mask，再运行 masked DROID-SLAM，尽量避免运动手部破坏静态场景假设。mask 由 HandCamSpaceMaskProvider 按帧生成；手漏检会使动态区域残留，mask 太大又会损失背景特征。因此手部误差不仅影响最终关节，还可能沿这条依赖链影响相机估计。

单目 SLAM 的重建存在尺度不确定性：只用图像匹配不能独立确定物体究竟更大更远，还是更小更近。当前代码用关键帧上的 Metric3D 深度预测估计尺度，流程如下：

traj, keyframes, disparity = masked_droid_slam(images, K, hand_masks)
for k in keyframes:
    depth_slam = 1 / disparity[k]
    depth_metric = Metric3D(image[k], K)
    scale[k] = est_scale_hybrid(depth_slam, depth_metric, mask[k])
s = median(scale)
t_c2w = s * traj.translation
R_c2w = quaternion_to_rotation(traj.quaternion)
T_w2c = inverse(T_c2w)

est_scale_hybrid 以两个深度场及 mask 估计关键帧尺度；当前入口的 sigma=0.5，初始 near / far 阈值为 0.4 / 0.7，遇 NaN 会放宽区间。片段最终使用关键帧尺度的中位数。这里是“先 SLAM，再通过预测深度恢复尺度”，不是每帧都用 MoGe 深度约束 MegaSAM 的另一条实验路线。文件名出现 moge 也不能替代对实际调用的判断：本 SLAM 函数实例化的是 Metric3D。

标准化后的 camera_trajectory.npz 保存 cam_c2w、其逆 cam_w2c、内参和时间映射。平移已乘尺度，后续不能再乘一遍。该尺度是模型估计的公制尺度，不是通过标尺或真值验证过的绝对尺度；如果 Metric3D 在低纹理或特殊场景中产生偏差，整段相机平移会相应偏大或偏小。

实现：hawor_slam.py · camera canonicalization

2.4 跨片段拼接：相机相似对齐，不是手部联合优化

每段独立 SLAM 都有自己的原点、朝向和尺度。拼接器用 source_frame_indices 找到相邻片段的共同帧，取相机中心对应点，用 SVD / Umeyama 类相似对齐将后片段映射到前片段已经对齐的坐标系。

mins,R,t ∑i∈overlap ‖cprev,i − (s R cnext,i + t)‖²R 为旋转，s 为正尺度，t 为平移。变换后的相机中心 c′ = sRc+t，相机朝向 R′cam = R Rcam。

对应点先中心化，对交叉协方差做 SVD，求旋转并修正反射；尺度由奇异值和源点方差计算，再由质心差恢复平移。代码是按相邻片段逐段对齐，不是全序列 bundle adjustment，也不是包含手部观测的联合优化。

这里还有一个容易忽略的耦合：相机经过 Sim(3) 缩放，而手部仍是选中的相机系结果。相机平移尺度与手部深度是否一致，需要另行检查；拼接没有共同优化它们。相机中心几乎不动、但头部持续旋转的片段，也不能仅凭位置对齐残差小就认定朝向可信。stitch_report.json 中的 overlap 数、方法、尺度和残差应作为必要的验收证据。

2.5 世界系变换，以及误差如何叠加

世界对齐前，代码要求手与相机的帧号、源帧号一致，时间戳以 rtol=0, atol=1e-6 检查。随后生成或加载手部几何，逐点做刚体变换；腕朝向通过旋转矩阵相乘变换。

pw,t,h,j = Rc2w,t pc,t,h,j + tc2w,tRw,hand = Rc2w Rc,handt：时间；h：左 / 右手；j：关节点。episode_world 是本视频的重建世界系，不是所有视频共同的地理或机器人基坐标系。

这个变换能够补偿相机运动，但不会自动消除输入误差。对小旋转扰动，一阶近似可以写为：

δpw ≈ R δpc − R[pc]× δθ + δt三项依次是手部重建误差、相机旋转误差引入的位置误差、相机平移 / 尺度误差。它们不是彼此独立的质量保证。

例如目标距相机约 0.5 m，1° 旋转误差造成的位置偏差量级约为 0.5×π/180 ≈ 8.7 mm，具体取决于误差轴和手的位置；这只是几何敏感性示例，不是实验测量。固定尺度误差、随时间变化的尺度漂移、相机旋转偏差和手部深度偏差会产生不同的伪运动，不能一概归因于“SLAM 不准”。

针对“手静止、头在动”的片段，应同时检查世界系手腕残余位移、其与相机运动的相关性、重叠区一致性及重投影。只有重投影贴合仍不足以证明尺度正确：沿同一相机射线的不同深度，可以给出相近的二维投影。

实现：hand_to_episode_world.py

2.6 质量检查与有限修复：把可运行和可使用分开

QC 不需要真值，检查的是契约、数值和内部一致性。它能发现一部分异常，却不能证明重建在真实世界中准确。推荐流程先生成报告，再尝试有限修复，最后重新检查。

相机合法性 / 对齐一致性相机变换有效；世界手部与相机系输入、变换关系一致错误但自洽的相机和手部仍可能通过

当前 repair 针对 hand_orientation_single_frame_outlier：连续三帧有效，中间帧与两侧差异大、而两侧可连贯衔接时，用相邻两帧的旋转中点替换异常腕朝向。实现保留已有几何，不是重新优化所有关节，也不修复长遮挡、手别身份交换或全局深度偏差。

推荐 recipe 暂不做 world-space smoothing。原因是现有平滑器可以独立改变对齐后的手腕，而没有同步更新相机变换 / 一致性模型，可能破坏 alignment_consistency。这是当前实现的约束，不是“平滑在原理上不可用”。重新引入时需要把几何与契约一起验证。

还有两层 mask 必须分开：导出的 valid_mask 是上游有效性；QC 的 bad-frame / bad-segment 是额外诊断。导出器不会自动把全部 QC 警告都合并成 invalid。训练时若需要质量过滤，必须明确规则，并保存过滤前后覆盖率，不能无声地把缺失值补成可信监督。

实现：QC checks · orientation repair · 最终 disposition

3. 如何评估：先固定协议，再讨论“精度”

可视化、QC 和有真值的定量评测回答不同问题。可视化帮助定位现象；QC 检查内部契约；真值评测才估计几何误差。比较两种方法时，还要避免“只留下各自最好的帧”或“用真值对齐抹去最关心的尺度误差”。

3.1 手部：覆盖、位置和手型必须分别报告

记 mt,h 为预测有效性，gt,h 为真值可用性。误差通常在预先约定的共同有效集合 V 上计算，覆盖率则必须说明分母：全视频帧、真值可见帧，还是左右手总样本数。只有原始 valid_mask 时，我们报告的是输出覆盖，不是检测召回率。

Coverageany = (1/T) ∑t 1[mt,L ∨ mt,R]MPJPE = (1 / (21|V|)) ∑(t,h)∈V ∑j=0…20 ‖p̂t,h,j − pt,h,j‖₂MPJPE 的单位、所在坐标系、是否做序列对齐，必须与数值一起记录。帽号表示预测值。

未根对齐关节误差同时受手型和整体位置影响；手腕误差单独衡量根位置；root-aligned 误差先分别减去预测和真值腕点，再比较关节，用于隔离相对手型。它只去平移，不等同于额外拟合旋转和尺度的 Procrustes / PA 指标。将三者放在一起，才能判断主要问题是“整只手放错位置”，还是“指关节形状本身不对”。

对长尾错误，至少保留 mean、median、P90、max 和异常片段；对时序，检查身份切换、缺失长度、拼接边界位移以及静止手残余运动。不同方法除共同帧上的误差外，还应同时给出各自覆盖和固定 GT 可见集合上的成功比例，避免低覆盖方法因只输出容易帧而显得更精确。

8.2 多卡 / 多机：按 episode 分片，而不是直接加线程数

推荐一个 GPU worker 固定一个 CUDA_VISIBLE_DEVICES，按互不重复的 episode 队列运行。同一个 episode 的 manifest 只能有一个 writer，不能让两台机器同时修改同一份 episode.yaml。本仓库的 scripts/run_four_gpu.sh 读取 schedules/gpu_0.txt 等队列，并为 episode 加锁。

--workers 是调度并发参数，--gpu-workers 限制 GPU 类任务数量，都不自动把外部进程均匀分配到不同物理 GPU。仅把后者改成 4，可能让四个 HaWoR 进程挤在同一张卡。多机也应划分不重叠队列，统一数据版本、持久路径和锁 / 完成状态，而不是共同扫描后各自抢跑。

HaWoR 推理、SLAM 和深度估计都消耗 GPU，但吞吐还可能受视频解码、CPU、模型初始化和共享存储限制。多卡主要增加独立视频的吞吐，不保证单视频延迟线性下降。估算时间应先量一个代表性批次的端到端速度与失败率，再用“剩余视频时长 × 实测计算倍率 ÷ 实际并发利用率”估算；不能用上节 MegaSAM 的单次耗时替代当前主线实测。

9. 结论：已有可交付链路，尚无更高精度的证明

当前系统已经具备把第一视角视频转换为标准化世界系手部资产的工程链路。其主要价值是把模型输出接入可解释、可恢复、可对齐的数据处理系统，而不是提出一个已经验证优于 HaWoR 的新重建模型。历史记录说明多数帧能够得到手部结果，但位置 / 深度误差、身份与时序失效以及相机尺度仍是关键限制。

对于“是否足够用于训练”，需要在现有 converter 上固定表示与过滤协议，再用受控训练实验回答。对于“是否优于 HaWoR / VITRA”，需要以下同口径比较；目前没有这组结果，不能用可视化观感或工程完成度代替。

当前最稳妥的交付结论：可以交付可追溯的几何标注和待审样例，不能把它们称作逐帧真值；可以开展 converter 对接和小规模使用验证，不能宣称全量数据已合格或精度已超过现有方法。
